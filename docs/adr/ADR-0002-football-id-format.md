# ADR-0002 (rev. 2) — Football ID: fully opaque identifier

## Revision note

Rev. 1 proposed `FID-<YY><region><checksum>`, encoding issuance year and issuing
region into the display code. The Council rejected that at G0: an identifier
that carries business facts becomes a de-facto data source, will be parsed by
downstream systems, and turns historical facts into permanent, unrevisable
attributes of a minor's identity. **Rev. 2 removes all business semantics from
both identifiers.**

## Context

Football ID is the single source of truth for a Person's football identity and
must last a lifetime, across SSB, club, academy, association, and federation.

- **Machine identity** must be non-guessable, non-enumerable, and meaning-free.
  Most subjects are minors; an enumerable ID exposes the population to scraping.
- **Human identity** must be readable aloud at a registration desk, printed on a
  match sheet, and typed by a referee pitch-side on a poor connection.
- **No mutable or historical fact** (year, region, organization, birth cohort,
  gender, role) may be embedded in either identifier. Players move provinces,
  change organizations, and re-register; the identity must never imply otherwise.

## Decision

Two attributes, one identity — both fully opaque:

1. **`football_id`** — opaque, immutable, database-generated `uuid` (v4). The
   only value used in foreign keys, API paths, tokens, and events. Never parsed,
   never carries meaning, never changes.
2. **`display_code`** — immutable, human-readable, **randomly generated** code
   with zero encoded business information:
   `FID-XXXX-XXXX-CC`, e.g. `FID-7K3M-9QT2-58`.
   - Two 4-character blocks drawn from a CSPRNG over Crockford Base32 minus
     `I`, `L`, `O`, `U` (32-char alphabet, ~40 bits of entropy) — non-sequential,
     so population size and registration order are not disclosed.
   - `CC` — 2-character check suffix (ISO 7064 mod 97-10) to catch transcription
     errors at pitch-side data entry. It is a *structural* checksum only and
     encodes no business fact.
   - Generated by rejection sampling against a uniqueness index; collisions are
     retried, never resolved by adding a sequence.

`display_code` is a lookup and verification aid only. It is **never** a foreign
key and **never** an authorization subject. Both values are unique and immutable
for the lifetime of the Person.

Issuance year and issuing association remain first-class **data**, stored as
`issued_at` and `issuing_organization_id` columns on the issuance record and
exposed through the API — queryable, auditable, and correctable — never encoded
into an identifier.

## Options considered

| Option | Pros | Cons |
| --- | --- | --- |
| A. Opaque UUID only | Maximum safety, zero semantics | Unusable verbally/on paper; SSB staff will invent their own codes — a shadow identity system |
| B. Sequential human code (`FID-SS-2026-000123`) | Very readable | Enumerable — reveals total registrations and enables scraping of minors; region becomes stale on transfer |
| C. UUID + semantic display code (rev. 1) | Readable, region visible on paper | Encodes business facts into an immutable identifier; invites parsing; freezes a historical region into identity |
| **D. UUID + fully random checksummed display code (chosen)** | Safe machine identity, usable human identity, transcription-error resistant, zero semantics | Region/year require a data lookup rather than reading the code |

## Decision-rule evaluation

| Rule | A | B | C | D | Winner |
| --- | --- | --- | --- | --- | --- |
| 1. Nationally scalable | yes | collides across provinces | yes | yes, no central sequence | **D** |
| 2. Federation-integrable | poor (unspeakable) | good | good | good (printable, checksummed) | **D** |
| 3. Safe for child data | best | worst (enumerable) | leaks region/cohort of minors | best (meaning-free) | A / **D** |
| 4. Auditable | good | good | good | best (facts live in queryable columns) | **D** |
| 5. SSOT | yes | parses semantics out of the code | invites parsing | yes (code is non-authoritative) | **D** |

## Consequences

- Schema: `football_id uuid primary key default gen_random_uuid()` and
  `display_code text unique not null`, both immutable — enforced by a trigger
  rejecting `UPDATE` on either column.
- Issuance facts are columns, not characters: `issued_at timestamptz not null`,
  `issuing_organization_id uuid not null references organization(id)`.
- Issuance is a domain operation on the Person aggregate emitting
  `FootballIdIssued { football_id, display_code, issued_at, issuing_organization_id }`.
- Any downstream system found parsing `display_code` is in violation of this ADR.
- Lookup by `display_code` must be **rate-limited and authenticated** — it is a
  convenience index over minors and must not be an open public endpoint.
- Transfers change Membership only. Neither identifier is touched; `Journey`
  entries accumulate. This is the technical guarantee of "Player Owns The Journey".
- Region-based reporting reads Membership history, never the display code.
- The region-code registry required by rev. 1 is **no longer needed**.

## Compliance impact

DDD: Football ID is a Value Object owned by the Person aggregate root.
Event-driven readiness: `FootballIdIssued` is the anchor event of the ecosystem.
Child-data: the identifier discloses nothing about the child — no cohort, no
location, no ordering. Satisfies data minimisation in
[CONSENT-001](../contexts/identity/00-consent-model.md).

## North Star impact

Directly enables the "Football ID" component of Verified Active Players, and
protects the metric from inflation by making duplicate issuance detectable
through the issuance record rather than through identifier structure.
